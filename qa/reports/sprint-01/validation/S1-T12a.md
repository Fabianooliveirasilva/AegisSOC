## Defects

### QA-S1T12a-001 (S2): persistent-stack secrets unreadable by the container users
- Reproduction (throwaway project `aegissoc-qa-t12a`, secrets generated by `scripts/setup-secrets` into the export copy, never the real directory): files are `-rw------- fabiano` (uid 1000) in a `drwx------` dir. `docker compose -p aegissoc-qa-t12a up -d --wait` exits 1. Postgres loops with `docker-entrypoint.sh: line 21: /run/secrets/postgres_superuser_password: Permission denied`; redis loops with `FATAL CONFIG FILE ERROR ... 'requirepass' wrong number of arguments` (the cat failure is hidden, the message is misleading). Cleaned up with `down -v` on that project.
- Expected: `make setup && make up` yields healthy services. Actual: restart loop. Non-swarm compose bind-mounts secret files with host owner and mode; the long-syntax `uid/gid/mode` is not applied.
- Why the disposable stack works: `make test-db-up` chmods its files to 644 (inside a 700 dir), which setup-secrets does not.
- Fix options for the implementer (not applied): make the persistent files readable by uid 70 and 999 (for example setup-secrets writes 644 into the 700 dir, or a documented chgrp/ACL scheme), or have an entrypoint wrapper copy secrets. Add an explicit readable-secret check with a clear error, and make the redis entrypoint fail loudly if the password file is empty. The decision touches SR-16 (secret file mode) and belongs to the maintainer/security reviewer. Not tested: persistent stack healthy with fixed permissions (same service definitions as the overlay, which is healthy).
- Impact: does not affect the disposable DB (T04-T10 integration tests). Blocks S1-T12 and any `make up`.

### QA-S1T12a-002 (S3): protocol §6 migration cycle cannot be run as written from the host
- Postgres and redis publish no port (correct per SR-24/DEPLOYMENT §4) and the network is internal, so `localhost:5432` is not available, and nothing in the repo tells a host process the host, port or passwords. `make test-db-up` only prints the secret directory; no env file, URL or target exists.
- What works today (verified): the host can reach the container over the bridge IP (`docker inspect aegissoc-test-postgres-1 --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'` gave 172.18.0.2; TCP connect to :5432 succeeded). So, manually: (1) `make test-db-up`; (2) in apps/api set `AEGIS_DATABASE_URL=postgresql+asyncpg://aegis_owner@<ip>:5432/aegissoc` and a `*_PASSWORD_FILE` pointing at `$XDG_RUNTIME_DIR/aegissoc-test-secrets-$(id -u)/postgres_owner_password` (aegis_owner for alembic; aegis_app for the app checks, which uses `AEGIS_DATABASE_PASSWORD_FILE`); (3) `alembic upgrade head`, assertions, `alembic downgrade base`, assertions, `upgrade head` again; (4) `make test-db-down`. The IP is not stable across runs. Alternative without host networking: run alembic in a container attached to `aegissoc-test_app_net`, but the network is internal so dependencies must already be in the image.
- Missing for a repeatable cycle: a documented, scripted way to get the host address and password-file paths (for example a `make test-db-env` target that prints URL and secret paths, or a loopback-only `127.0.0.1:` publish in a test-only overlay, which needs maintainer/security agreement because SR-24 says no published ports), a decision on which role alembic uses (aegis_owner password variable is not in the current config model: `database_password_file` is a single setting), and a `make` target or script for the cycle. Also, alembic `env.py` URL source for the owner role is T04's design, so T04 needs this before QA can run §6 at all.
- Impact: T04 QA cannot execute the cycle without the manual workaround above; raise with the orchestrator before T04 starts.

### QA-S1T12a-003 (S4): aegis_app can connect to other databases
- `aegis_app` connected to the default `postgres` database (PUBLIC keeps CONNECT). Not required by the roles spec, so not a failure; suggestion: `REVOKE CONNECT ON DATABASE aegissoc, postgres FROM PUBLIC` then grant to aegis_app/aegis_owner, for SR-27 least privilege.

## Notes and challenged assumptions
- Test secret files are mode 644 so any container UID can read them; protection relies on the 700 parent dir under `$XDG_RUNTIME_DIR` (fallback `/tmp`, where `mkdir -m 700` fails closed if the path pre-exists). Fixed per-user path means two simultaneous runs (parallel agents or CI) collide, and `test-db-up` always tears down the previous disposable stack first. Acceptable for a serial workflow; note for T13.
- Test overlay `restart: "no"`: after a host reboot the stack is gone by design (tmpfs).
- Postgres listens on `*` inside the internal network; reachable only from containers on `aegissoc-test_app_net` (and the host through the bridge IP, see QA-002). Healthcheck (`pg_isready` TCP) does not authenticate, so it proves liveness and completed init, not credentials. I verified credentials separately.
- Containers named `aegis-sec-t12a-*` that were present belong to the security reviewer; not touched.
- Not tested: backup/restore, upgrade, Redis AOF replay after restart on persistent volume, concurrency of two `test-db-up` runs.

### QA-002 migration cycle, run as far as possible
Executed from the host against the fresh disposable DB using only values from `make test-db-env`: (1) owner `create table public.qa_probe` + index (stands for `upgrade head`); (2) as aegis_app: DML fails until the owner grants (stands for the app assertions); after `GRANT SELECT,INSERT,UPDATE,DELETE` DML works and DDL/TRUNCATE still fail; (3) owner `drop table` (stands for `downgrade base`), table count 0; (4) re-create and drop again (`upgrade head` again). All OK. Not run (needs T04): alembic itself and its `env.py`. Remaining for T04: (a) the config model has one `database_password_file`, but migrations need the aegis_owner password and the app needs the aegis_app password, so T04 must define how alembic selects the owner secret (e.g. a second setting or env var fed from `AEGIS_TEST_PG_OWNER_PASSWORD_FILE`); (b) the IP changes on every up, so the integration fixtures must call `make test-db-env` (or parse it) each run; (c) there are no default privileges, so the T04 migrations must GRANT per table explicitly (and only SELECT/INSERT on `audit_log`, DATABASE_DESIGN §4/§12); (d) `statement_timeout` and the SECURITY DEFINER functions are T04; (e) a scripted target for the cycle does not exist (propose in T04 or T13).

### Notes (S4, not blocking)
1. Because aegis_app has no default privileges, a test that only creates a table as owner and reads as app fails; this is intended, but T04 authors must know. (Not a defect.)
